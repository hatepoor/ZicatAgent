## 0. 核心公理 (Core Axioms - 最高优先级)
1.  **行动验证原则 (Action-Verified Only)**
    *   **定义**：任何写入 L1/L2/L3 的信息，必须源自**成功的工具调用结果**（如 `shell` 执行成功、`file_read`/`memory_read` 确认内容存在、代码运行通过）。
    *   **禁止**：严禁将模型的“固有知识”、“推理猜测”、“未执行的计划”或“未验证的假设”作为事实写入。
    *   **口号**：**No Execution, No Memory. (无行动，不记忆)**
2.  **神圣不可删改性 (Sanctity of Verified Data)**
    *   **定义**：凡是经过行动验证的有效配置、避坑指南、关键路径，在重构（Refactoring/GC）时**严禁丢弃**。
    *   **操作**：可以压缩文字、可以迁移层级（从 L2 移到 L3），但绝不能丢失信息的准确性和可追溯性。
    *   记忆修改时请极度小心，不要 overwrite 或 code run。修改一律走 `memory_patch`（旧版本自动保留），改不动宁愿不改。
3.  **禁止存储易变状态 (No Volatile State)**
    *   **定义**：严禁存储随时间/会话高频变化的数据。
    *   **示例**：当前时间戳、临时 Session ID、正在运行的 PID、某个具体绝对路径、连接的设备信息
4.  **最小充分指针 (Minimum Sufficient Pointer)**
    *   上层只留能定位下层的最短标识，多一词即冗余。

## 记忆工具（唯一读写入口）

记忆存在 SQLite（`memory/memory.db`），**不要再用 file_read/file_write/file_patch 操作 `memory/`**：

| 操作 | 工具 |
|---|---|
| 查有什么 | `memory_search(query=...)` / `memory_index()` |
| 读正文 | `memory_read(name)` |
| 新建 | `memory_write(name, layer, kind, body, summary=...)` |
| 修改 | `memory_patch(name, body=..., reason=...)`（自动记版本） |
| 移除 | `memory_archive(name, reason=...)` |
| 建立关系 | `memory_link(from, to, rel)` |

说明：
- `layer` 取 L1/L2/L3/L4；`kind` 取 fact/sop/script/insight。
- L1 索引由记忆库**动态渲染**，不需要手工维护列表；唯一可编辑的是 `l1_rules` 条目里的 RULES 段（用 `memory_patch("l1_rules", ...)`）。
- 写入受 256KB 上限约束；脚本类（kind=script）初始为 draft，验证执行通过后再上线。
- 直接 `file_write`/`file_patch` 到 `memory/` 会被引擎拒绝，请只用 `memory_*` 工具。

## 记忆层级架构
```
L1: 记忆库索引 (动态渲染 - ≤30 行，含 RULES)
    ↓ 导航指向 (Pointer)
L2: 记忆库 fact 层 (环境事实/配置/凭证引用)
    ↓ 详细引用 (Reference)
L3: 记忆库 sop/script 层 (专项 SOP 与技能脚本)
L4: 记忆库 archive 层 (历史会话摘要；原始文本留在 memory/L4_raw_sessions/)
```

## 各层职责与原则
### L1：全局内存索引（记忆库动态渲染）
**职责**：为 L2 和 L3 提供极简导航索引，确保关键能力可被发现。
**特征**：
- 体积限制：≤ 30 行（硬约束），< 1k tokens（期望）。严禁填写细节（除非极高频任务）
- 内容：两层「场景关键词→记忆定位」映射 + RULES（红线规则 + 高频犯错点）
  - 第一层：高频场景 key→value（直接给出 sop/py/L2 条目名），自包含名称只写一词不重复翻译
  - 第二层：低频场景仅列关键词，需要时 `memory_search` / `memory_read` 自行定位
  - 核心：场景触发词极重要（不索引则不知有此能力），但严禁写How-to细节
  - RULES：压缩版避坑准则，包含：
    - 红线规则（致命型）：违反会导致进程终止或系统崩溃（如 `禁无条件杀python(会杀自己)`）
    - 红线规则（隐蔽型）：违反不报错但产生错误结果（如 `搜索用google不用百度`）
    - 高频犯错点：容易遗忘的关键约束（如 `es(PATH有)` 防止找路径）
- 更新：L1 列表**自动生成**，不要手工增删行；只允许 `memory_patch("l1_rules", body=...)` 更新 RULES 段。
**禁止**：严禁写入密码、API Key。允许内联非敏感触发参数（如代理端口）。不写 "How to" 或详细解释。严禁包含特定任务的技术细节（特定任务细节应该在L3）。更加严禁写入日志记录！
---
### L2：全局事实库（记忆库 kind=fact）
**职责**：存储全局环境性事实（路径、凭证、配置、常量等）。
**特征**：
- 趋势：随环境扩展而膨胀（可接受）
- 内容：每条事实一个条目（`memory_write(layer="L2", kind="fact", ...)`），正文可用 `## [SECTION]` 组织
- 同步：新增/修改事实后无需改 L1，索引自动出现
**禁止**：禁止存储易变状态、禁止存储猜测、严禁存储大模型可推理的通用常识
---
### L3：任务级精简记录库（记忆库 kind=sop/script）
职责：补充 L1/L2 无法容纳、但对**特定任务**未来复用至关重要的少量详细信息。内容必须在满足复用需求的前提下**尽可能短**。
原则：
- 只记录：**跨会话**仍重要、且难以通过少量 `memory_read` / `web_scan` / 简单脚本快速重建的要点。
- 优先写：该任务特有的隐藏前置条件、典型易踩坑点，一旦遗忘会导致高成本重试的信息。
- 不记录：普通操作步骤、可在几步探测中重新获得的路径或状态信息。不记录项目特定事实（不符合跨会话要求，应当放入项目目录中）
- L3 SOP更新：应当越更新越精华越短，而非追加
形式：
- SOP（kind=sop）：为单一任务或小类任务保留极简的「关键前置 + 典型坑」清单，避免长篇教程。
- 工具脚本（kind=script）：仅封装高复用、逻辑相对复杂且不希望每次都重新推理的处理流程；执行前由引擎物化到 `temp/skills/`。

## L1 ↔ L2/L3 同步规则（已自动化）
| 操作 | 同步方式 |
|---------|--------|
| L2/L3 新增/删除/修改 | 写库即可；L1 列表由 `memory_items` 自动渲染 |
| 发现通用避坑规律 | 用 `memory_patch("l1_rules", body=...)` 追加一句 RULES |
| 归档旧条目 | `memory_archive(name)`，L1 自动消失 |

> **同步红线**：L1 只写关键词/名称，禁搬细节。括号内只写反直觉的场景触发词(2-4字)，禁写机制/方法/步骤。需要评估L1中的token数和索引效用。
> 反例：❌ sop_name(场景A:方法1+方法2+方法3) → ✅ sop_name(场景A)
> 反例：名字已自解释时 ❌ discord_slate_sop(Slate输入框) → ✅ discord_slate_sop
> **99% sop仅通过自解释名字索引，不需要触发词！**
> 大量同类sop应当合并并概括性索引，无需列举！

## 信息分类快速决策树
```
"这条信息该放哪层？"

是『环境特异性事实』? (IP、非标路径、凭证、ID、API 密钥等，大模型 Zero-shot 无法生成准确)
  ├─ YES → L2：memory_write(layer="L2", kind="fact", ...)
  │        然后 → L1 自动索引，无需手工加行
  │
  └─ NO
       ↓
       是『通用操作规律』? (全局性避坑指南、排查方法、不针对特定任务的通用准则)
       ├─ YES → L1 RULES：memory_patch("l1_rules", body=...)（仅限 1 句压缩准则）
       │
       └─ NO
            ↓
            是『特定任务技术』? (艰难尝试才能成功，且未来还能用到的任务，如：微信解析参数、特定游戏坐标、临时工具配置)
            ├─ YES → L3：memory_write(layer="L3", kind="sop"/"script", ...)
            │
            └─ NO → 判定为『通用常识』或『冗余信息』: 严禁存储，直接丢弃
```
