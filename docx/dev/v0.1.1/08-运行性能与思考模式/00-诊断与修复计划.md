## 0. 结论摘要

三个问题不在同一层，但会互相放大：

1. **memory 工具慢**：确有可消除的写放大（每条命中一个写事务、`access_count` 更新触发整行 FTS 重建、L1 连接泄漏）；但当前库只有 37 条、68.7KB，读查询 <0.5ms，**“慢”很可能有相当一部分是模型思考时间**，需要计时归因。
2. **CPU 高、风扇响**：最可能的主因是前端每个 token 都触发全量文本净化 + 整段 Markdown/KaTeX 重渲染，以及 App 根部 1Hz 时钟导致整树每秒刷新；其次是后端逐 token 转发和每 super-step 的 checkpoint/lzma。
3. **`/effort` 与 thinking**：配置链路已存在但白名单缺失；LangChain 上游把 `reasoning_content` 丢了；RPC 和前端都没有 thinking 协议。

**本轮范围**：先修 CPU + memory。
**本轮已追加**：`/effort` 选择页 + DeepSeek 接口（手动选择 provider）。
**thinking**：实时折叠显示 + 历史回放已落地（见 0.3）。

## 1. 问题现象

### 1.1 memory 工具调用时间长

- 运行时 `memory_search` / `memory_read` 等工具返回慢，不能及时看到结果。
- 不是“偶发一次”，而是使用中持续可感。

### 1.2 系统资源占用高

- 笔记本风扇持续响，使用 Web UI 时更明显。
- 空闲（页面开着但不发任务）也有持续负载。

### 1.3 思考强度不可控、thinking 不可见

- deepseek 等模型在未显式设置思考模式时，按渠道默认 high 思考。
- 缺 `/effort`，用户不能手动调低/关闭。
- 即使模型在思考，前端也没有 thinking 内容，默认折叠、呼吸灯提示都没有。
- 用户添加模型时，缺少手动指定思考模式的入口。

## 2. 诊断结论

标记含义：

- ✅ 代码或实测可直接证明
- ⭕️ 很可能，但依赖运行态或尚未定量
- ❓ 目前无法确定，需要探测/计时

### 2.1 memory 工具慢

| 标记 | 结论 | 证据 |
|---|---|---|
| ✅ | 不是数据规模问题：当前 `memory_items=37`、body 合计 68.7KB、最大 9.48KB；只读查询 <0.5ms | 实测 `memory/memory.db` |
| ✅ | `memory_search` 对每条命中单独开一个写事务 | `memstore/tools.py:45` → `memstore/repository.py:228` |
| ✅ | `access_count` 更新会触发整行 FTS 重建：`trg_items_fts_upd` 是 `AFTER UPDATE`，没有 `WHEN` 限定 | `memstore/schema.sql:109` |
| ✅ | `memory_read` = 3 次读 + 1 次写 + `version_count`；读侧没有 body 上限 | `memstore/repository.py:215`、`memstore/tools.py:53` |
| ✅ | `load_L1()` 每次新建 SQLite 连接且从不 close；`render_l1(log=True)` 还同步写一条 event | `zicat.py:35`、`memstore/tools.py:31`、`memstore/repository.py:268` |
| ✅ | `/memory` 命令同样每次新建 `Database`，没有 close | `core/commands.py:308` |
| ⭕️ | 跨连接写锁最坏等 `busy_timeout=5000`；单用户下是否真的排队取决于并发 | `memstore/db.py:22`、`memstore/tools.py:105` |
| ❓ | 你感知的“工具慢”中，DB 时间与模型思考时间各占多少，目前没有计时数据 | 需要 `ZICAT_DEBUG_TIMING` |

**结论**：写放大是真实存在的，但它未必是“慢”的全部。先修写放大，同时加计时点，避免把模型思考误判为 DB 慢。

### 2.2 CPU 高、风扇响

| 标记 | 结论 | 证据 |
|---|---|---|
| ✅ | 前端每个 `delta` 都 `patch` 整个 entries、对**全量累积文本**跑 `cleanAssistant` / `extractSummary`，并触发整段 Markdown+KaTeX 重渲染 | `ui/src/hooks/useAgentSession.ts:202`、`ui/src/core/text.ts:39`、`ui/src/components/Rich.tsx:9` |
| ✅ | `App` 根部 `useClock()` 每秒更新，导致整棵组件树每秒重渲染；`RightPanel` 每次 render 都 filter entries | `ui/src/App.tsx:45`、`ui/src/hooks/useClock.ts:7`、`ui/src/components/layout/RightPanel.tsx:22` |
| ✅ | 后端每个 token 一次 `json.dumps`+flush，Node 逐条 SSE 转发；`tok_buf["text"] += delta` 是全量字符串拼接 | `engine/runner.py:229`、`core/rpc.py:55`、`ui/server.mjs:68` |
| ✅ | 每个 super-step 做 checkpoint + lzma；`LoggingCallback` 每轮把整份 Prompt 追加到单个文件（实测 10.6MB） | `engine/checkpointer.py:16`、`engine/callbacks.py:48` |
| ⭕️ | 长会话下 checkpoint/lzma 是 Python 侧主要本地成本；没有 profiler 百分比 | 需实测 |
| ❌ | `Spinner` 的 80ms `setState` 只重渲染自身，不是主因 | `ui/src/components/chat/Spinner.tsx:8` |
| ❌ | 已排除：scheduler 120s、psutil 扫描、UI 轮询、Node 频繁 spawn Python（检查时这些进程都没跑） | 运行态检查 |
| ⭕️ | 浏览器工具 `web_scan` / `web_execute_js` 是条件性尖峰：整页 HTML 双解析 + 元素级 diff + 页面内 450ms 全 DOM 扫描 | `simphtml.py:816`、`tools/browser/__init__.py:41` |

**结论**：先做前端合批和时钟隔离，收益最大、风险最低；后端 token 合批紧随其后；checkpoint/日志先测量再决定是否动。

### 2.4 渠道探测结果（2026-10-28）

探测方式：当前模型配置，`max_tokens=8`，消息 `Say OK.`，分别测试非流式与流式。

| 项 | 结果 |
|---|---|
| 渠道 | `https://api.commandcode.ai/provider/v1` |
| 模型 | `deepseek/deepseek-v4.1-flash` |
| 非流式 `high` | 200；`message` 字段：`content`、`reasoning_content`、`role`；`reasoning_content` 有内容 |
| 流式 `high` | 200；`delta` 字段：`reasoning_content`、`role`；首个 reasoning chunk 为 `The` |
| `off` | 200；无 `reasoning_content` |
| `low` / `medium` / `max` | 200；均有 `reasoning_content` |
| `none` / `minimal` | 400；错误信息列出合法值 `off|low|medium|high|xhigh|max` |
| `usage` | `completion_tokens_details.reasoning_tokens` 会给出思考 token 数 |

**结论**：

1. `off` 直接发 `reasoning_effort="off"` 即可，不需要 `none`/`minimal` 兜底。
2. 渠道还支持 `xhigh`，可作为 `max` 之外的更高档，但用户本轮只要求 `off/low/medium/high/max`。
3. 字段名就是 `reasoning_content`；`reasoning` / `reasoning_details` 别名不需要，但子类可保留兼容判断。
4. `langchain_openai 1.7.2` 仍会丢弃该字段，下一轮必须加 `ChatOpenAI` 子类，不能只改 runner。

## 4. 修复计划

### 阶段 0：基线与备份

1. 备份记忆库：`python -m memstore.backup`，确认 `memory/backup/` 有新快照。
2. 记录基线：
   - `memory.db-wal` 大小；
   - 连续 50 次 `memory_search` / `memory_read` 的 p50/p95；
   - 一段长回答流式期间浏览器进程 CPU；
   - 一次 1k token 回答产生的 RPC/SSE 事件数。
3. 增加临时计时开关（可保留）：
   - `ZICAT_DEBUG_TIMING=1` 时，在 `MemoryTools.dispatch` 和 `ToolRuntime.run_tool` 打印 `[timing] name db_ms total_ms`；
   - 默认关闭，不影响正常输出。

### 阶段 A：memory 写放大

#### A1. FTS 触发器加 `WHEN` + schema v2

- `memstore/schema.sql`：
  - `trg_items_fts_upd` 增加：
    ```sql
    WHEN old.name IS NOT new.name
      OR old.title IS NOT new.title
      OR old.summary IS NOT new.summary
      OR old.body IS NOT new.body
    ```
  - 只更新 `access_count` / `last_access_at` / `priority` / `status` 时不再重建 FTS。
- `memstore/db.py`：
  - `SCHEMA_VERSION = 2`。
  - 迁移时 `DROP TRIGGER IF EXISTS trg_items_fts_upd`，重跑 schema，再写 `PRAGMA user_version=2`。
  - 迁移前必须先备份。
- 测试：
  - 新建 v1 库 → 打开触发迁移 → 断言触发器 SQL 含 `WHEN`；
  - `UPDATE memory_items SET access_count=access_count+1` 后 FTS 内容不变。

#### A2. `memory_search` 合并为一次写事务

- `memstore/repository.py` 新增 `touch_many(ids, actor="agent", event="read")`：
  - 一个 `BEGIN IMMEDIATE`；
  - 一条 `UPDATE ... WHERE id IN (...)`；
  - 批量 `INSERT memory_events`（每个 id 一条，保留审计粒度）。
- `memstore/tools.py` 的 `memory_search` 改为一次 `touch_many(...)`，不再循环 `touch`。
- 测试：monkeypatch `touch_many`，断言一次搜索只调用一次；5 条命中仍有 5 条事件。

#### A3. `memory_read` 减少往返

- `memstore/repository.py` 新增 `read_with_meta(name_or_id, actor)`：
  - 一次 `get`；
  - 一次 `touch`（现在 FTS 不重建，成本很低）；
  - 一次 `version_count` 合并返回。
- `memstore/tools.py` 的 `memory_read` 改用它，返回结构不变。
- 保留 body 256KB 上限，不截断正文（SOP 需要完整内容）。

#### A4. L1 连接复用

- `zicat.py` 增加模块级单例 `_L1_STORE`（`threading.Lock` 保护初始化）。
- `load_L1()` 复用该单例；注册 `atexit` 关闭。
- `core/commands.py` 的 `_cmd_memory` 用 `try/finally` 关闭自己创建的 `Database`。
- 验证：连续调用 `load_L1()` 20 次，连接数/WAL 不持续增长；`/memory index` 正常。

#### A5. 验收

- `python -m memstore.verify`：当前 134 项中 6 项失败；迁移前快照同样失败（`facts`/`l1_rules` 漂移 + 2 个 manifest 外条目），不是本轮引入。本轮新增的触发器/读写测试全绿。
- 微基准：50 次 `memory_search` / `memory_read`，对比修改前后 p50/p95。
- 预期：search 写事务从 N 次降到 1 次；`access_count` 更新不再触发 FTS 重建；WAL 不因泄漏连接持续膨胀。

### 阶段 B：CPU 降低

#### B1. 前端 delta 合批

- `ui/src/hooks/useAgentSession.ts`：
  - 新增 `deltaBuffer` / `deltaTimer` refs。
  - `delta` 事件不再逐 token `patch`；首次 delta 立刻创建 assistant entry，之后用 `setTimeout(50ms)` 或 `requestAnimationFrame` 合并刷新。
  - 在 `tool_call`、`assistant`、`done`、`interrupt`、`notice` 前强制 `flushDelta()`，保证不丢字、不串轮。
  - `extractSummary` 仅在文本包含 `<summary>` 时执行。
- 预期：状态更新次数从每 token 一次降到每 50ms 一次；长回答的 O(n²) 成本显著下降。

#### B2. 时钟隔离

- `ui/src/App.tsx` 移除 `useClock()` 和向 `StatusBar` / `RightPanel` 传的 `now`。
- `StatusBar`、`RightPanel` 各自内部 `useClock()`；App 不再每秒重渲染整棵树。
- `RightPanel` 的 `entries.filter` 用 `useMemo` 缓存。

#### B3. Markdown 渲染稳定化

- `ui/src/components/Rich.tsx`：
  - `remarkPlugins`、`rehypePlugins`、`components` 提到模块级常量；
  - `export default memo(Rich)`。
- `ui/src/components/chat/EntryView.tsx`：
  - `memo` 包装；
  - `onPickCandidate` 若身份不稳定，用 `useCallback` 或自定义比较器忽略函数变化。
- `AssistantBlock` 已有 `useDeferredValue`，保留。

#### B4. 后端 token 合批

- `engine/runner.py` 的 `_consume`：
  - 用 `_DeltaBatcher`（list 缓冲 + `time.monotonic()`）按 80 字符或 40ms 合并 `delta_token`；
  - 在 `updates` / `done` / 中断前 flush；
  - 删除 `tok_buf["text"] += delta` 的全量字符串累计，改为布尔 `tok_seen`，消除 O(n²) 拼接。
- `core/rpc.py` 继续使用 `delta` 事件，无需新增协议。
- `engine/callbacks.py`、`engine/checkpointer.py` 先不改；本轮结束后若 CPU 仍高，再做 P2：日志文件轮转、压缩阈值/级别调整。

#### B5. 验收

- `cd ui && npm run build` 通过。
- 手工长回答：浏览器 CPU 明显下降；文字仍然连续，不出现整段延迟。
- `pytest tests/test_runner_stream.py`，新增合批测试：模拟 100 个 token，断言事件数显著少于 token 数且文本无丢失。

## 6. 风险与回滚

| 风险 | 处理 |
|---|---|
| 数据库迁移失败 | 迁移前 `memstore.backup`；只重建一个触发器，失败用备份恢复 |
| delta 合批丢字/串轮 | 所有边界事件强制 `flushDelta()`；加“文本无丢失”测试 |
| memo 化后不更新 | 回调用 `useCallback` 或自定义比较器 |
| 前端合批导致流式不够“顺” | 50ms 合批肉眼不可辨；可按需调到 30ms |
| checkpoint/日志改动影响 rewind | 本轮不动；先测量再决定 |

**回滚**：改动分两个提交（memory、CPU），任一阶段失败可单独 revert；数据库用备份恢复。
