# 04 · 优化路线图(O1~O10)

> 依据:2026-10-28 实测耗时数据(01/03 篇)+ 业界对比(browser-use、Playwright MCP、nanobrowser、BrowserOS)
> 当前体感:新会话首调 web 工具 ~6s,单次扫描 1~3s(大页面模型消化另计),偶发 15s 超时

## 耗时去向基线

| 环节 | 实测/机制 | 属性 |
|---|---|---|
| 扩展重连(agent 进程每次重启) | 5~6s(alarm ~5s 一轮) | 固定税 |
| 模型消化 `web_scan` 返回(默认上限 35000 字符) | 数秒 + 费钱 | 隐形大头 |
| 后台标签页节流 → execute_js 超时 | 至多 15s | 灾难个案 |
| `importlib.reload(simphtml)`(每次扫描)、0.2s 结果轮询 | ~0.1~0.3s | 零碎 |

## 第一梯队:体感(性能 + 省 token)

### O1 master 常驻化 ★收益最大
- **现状**:master 随 agent 进程生死,每次重启扩展都要重连 5~6s。
- **方案**:TMWebDriver 独立为后台常驻进程(项目已有 remote 机制与 `tmwebdriver_sop` 提法);agent 启动时检测 18766 无活 master 则自动拉起(Windows 后台进程),自身走 `_probe_remote` → remote 模式(HTTP 毫秒级往返)。
- **涉及**:`TMWebDriver.py`(或新增 sche_tasks 入口)、agent 启动钩子。
- **验收**:新会话首次 `web_scan` ≤1s;kill agent 重启不影响浏览器连接。
- **预估**:~1h。

### O2 扩展断线快速重连(O1 兜底)
- **现状**:ws 断开后等下一轮 alarm(~5s)才重试;alarms 可能被浏览器 clamp 到 30s+。
- **方案**:`background.js` 的 `ws.onclose` 改立即指数退避重连(0.5s/1s/2s/…,上限 5s),alarm 仅作保底。
- **涉及**:`assets/tmwd_cdp_bridge/background.js`(几行)。
- **验收**:kill master 再起,1~2s 内 `get_all_sessions` 恢复。
- **预估**:0.5h。

### O3 砍 token 三刀
- 页面缓存:`tabId+URL` 未变时跳过重抓(连续两次 scan 同一页面直接命中);注意跳转/动态页要可强制刷新。
- 去掉 `tools/browser/__init__.py` 每次调用前的 `importlib.reload(simphtml)`(开发期热载遗留,连带重 bs4 导入链)。
- 长页默认 `text_only` 或收窄默认 maxlen,要结构时再显式要 HTML。
- **验收**:重复 scan 同页 <100ms;典型页面返回字符数下降 ≥60%。
- **预估**:~1h。

### O4 可访问性树替代原始 HTML(借鉴 Playwright MCP)
- **方案**:注入脚本改为输出 ARIA/可访问性快照——只留可交互节点(`button[可点]`、`textbox[可填]`、链接文字)与层级,附编号;典型页面从 3.5 万字符降到数百~数千。
- **依赖**:与 O9(编号引用)配套;`simphtml.py` 新增模式而非替换,保留 HTML 模式兜底。
- **验收**:同一组页面 token 下降 50~80%,agent 完成同任务的动作成功率不降。
- **预估**:~2h(不含评测)。

## 第二梯队:安全与稳定

### O5 鉴权 ★安全必做
- **现状**:本地回环无鉴权,任何进程连 18765 即可读 cookie、执行任意 JS;扩展还会剥页面 CSP。
- **方案**:master 首启生成 token 存本地(如 `%LOCALAPPDATA%`/项目配置);扩展端经扩展 storage 配对一次;background 握手帧带 token,校验失败拒绝注册 session。
- **注意**:与 O2 同批改 `background.js`,一次重载扩展。
- **验收**:无 token 的外部 WS 连入被拒,日志留痕。
- **预估**:0.5h。

### O6 超时治理
- execute_js 默认 15s → 8s 快速反馈(结果轮询粒度 0.2s → 0.05s)。
- 后台标签页注入改走扩展 CDP 通道(`chrome.debugger` 的 `Runtime.evaluate` 不受页面定时器节流);先确认 `simphtml` 当前注入路径是否受节流影响,再决定切换范围。
- **验收**:后台标签页 execute_js 不再 15s 超时。
- **预估**:1~2h(含确认)。

### O7 端口可配置/自动避让
- 18765/18766 支持配置文件/环境变量;占用时自动顺延端口并在 remote 模式下正确传递(现硬编码,已加自愈与报错,但仍是单端口)。
- **预估**:0.5~1h。

## 第三梯队:能力打磨

### O8 原子动作短路
- 保持 2 工具形态:`web_execute_js` 接受 `{"action":"click|fill|scroll|extract_table|wait","selector":...,"value":...}`,服务端映射为预置 JS 片段;模型免手写 JS,省 token、少出错、快。自由 JS 仍是逃生门。
- **预估**:2~3h。

### O9 元素编号引用(与 O4 配套)
- `web_scan` 快照中可交互元素带 `[12]` 编号,`click(12)` 直接定位;编号在页面跳转后失效并提示重扫。
- **预估**:1~2h(依赖 O4 的快照结构)。

### O10 分发体验
- README 一步安装指引;`NO_TAB_HINT` 已带指引,再进一步:首次失败时 agent 直接打印可复制的安装路径命令;长期打包 .crx/上架 Edge/Chrome 商店,消掉"没装扩展"劝退点(开源新用户第一坑,2026-10-28 已实锤)。

## 建议排期

```
第一批:O1+O2+O3(~2.5h)  → 首调 6s→亚秒,单次扫描提速且省钱
第二批:O5(0.5h)          → 堵安全洞(与 O2 同批改扩展)
第三批:O4+O9(~半天)      → token 代差级下降 + 编号引用
随后:O6/O7/O8/O10 按需
```

全部落地后目标体感:新会话首调 ≤1s,常规扫描 1~2s 内返回且 token 减半以上,无 15s 级卡顿,本地攻击面闭合。
