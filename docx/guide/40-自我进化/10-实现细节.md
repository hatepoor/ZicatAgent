## 0. 先把"骨架"钉死：一次任务真实的控制流

所有"进化""执行力"的讨论都挂在下面这条链上（每一环都有行号）：

| 阶段 | 位置 | 关键事实 |
|---|---|---|
| 入口 | `agentmain.py:145-148` `put_task()` | 所有前端/反射/子 agent 都只做一件事：往 `ZicatAgent.task_queue` 塞一条 `{query, source, output}` |
| 单线程消费 | `agentmain.py:166-227` `run()` | **一个 ZicatAgent 实例只有一个 worker 线程**（`agentmain.py:265` 里 `threading.Thread(target=agent.run)`），天然串行 |
| 组装系统提示 | `agentmain.py:35-39` `get_system_prompt()` | `assets/sys_prompt.txt` + 日期 + `get_global_memory()`（即 L1 索引） |
| 系统提示真正送达模型 | `llmcore.py:1219-1226` `NativeToolClient.chat` → `set_system()` | 每轮把 `messages[0].content`（系统提示）重新塞进 `backend.system`，并拼上 `<summary>` 协议 `llmcore.py:1195-1204` |
| 主循环 | `agent_loop.py:42-106` | `max_turns` 默认 40（`agent_loop.py:43`），CLI 调用方传 180 |
| 工具分发 | `agent_loop.py:18-29` `dispatch()` | `do_{tool_name}` 反射；`bad_json` 有专门分支 |
| 收口 | `agent_loop.py:89-106` + `zicat.py:549-573` `turn_end_callback` | **每一轮结束都会经过这里**，所有周期提示/干预通道都在此注入 |

一个容易被忽略的细节：`agentmain.py:200-201` 只是"CLI 默认值"，`agent_loop.py:48` 会把 `handler.max_turns` 覆盖成传入值，所以**任何走 `agentmain.py` 的路径（CLI、`--task`、`--func`、`--reflect`）都是 180 轮**；只有直接 import `agent_runner_loop` 才用默认 40。任务描述里的"max_turns=180"仅在 `agentmain.py` 路径成立。

## 1. "自我进化"的可验证闭环

## 完整闭环（四个环节，逐环给证据）

```
[A] 召回：L1 索引每次 LLM 调用都在 system prompt 里
        agentmain.py:35-39 → zicat.py:581-591 get_global_memory()
        内容 = assets/l1_structure.txt（宪法 + 层级指针）
             + memory/l1_fallback.txt（L1 索引，实测 23 行）
        ↓
[B] 触发：任务结束时模型被工具描述"点名"去沉淀
        assets/tools_schema_cn.json:70 "超15轮完成的任务必须调用以沉淀经验"
        → zicat.py:509-521 do_start_long_term_update
        ↓
[C] 写入：注入 L0 元 SOP，由模型自己 file_write / file_patch
        zicat.py:516-518 把 './memory/memory_management_sop.md' 作为 L0 回填进工具结果
        zicat.py:511-514 next_prompt = get_global_memory() + 【记忆提纯】纪律 8 条
        ↓
[D] 下次复用：L3 文件被 L1 索引指向，模型 file_read 后
        zicat.py:444-445 强制提示"提取关键点（特别是靠后的）update working memory"
```

**[C] 是最关键的代码事实：仓库里没有任何一行代码会"自动生成 SOP"。**
代码对 `memory/` 的写入点只有两处：

- `zicat.py:158-166` `log_memory_access()` → 只写 `memory/file_access_stats.json`（访问计数），**且全仓无读取方**（grep 该文件名仅命中 `zicat.py:160` 本身）。这是"埋点但无消费者"的半成品。
- `agentmain.py:28-33` → 首次运行初始化 `memory/facts.txt`（L2）与 `memory/l1_fallback.txt`（L1，从 `assets/l1_template*.txt` 复制）。

也就是说：**"沉淀成 SOP"的实际写手是模型自身（`file_write`/`file_patch`），代码只负责"在该沉淀的时候把它按到桌前"**。这是"真进化 vs 提示词工程"的分水岭。

## 下一轮"召回"逐行看

1. `zicat.py:581-591` `get_global_memory()` 拼出：`cwd = .../temp (./)` + `[Memory] (../memory)` + `l1_structure.txt` 全文 + `l1_fallback.txt` 全文。
2. 该文本作为系统提示一部分（`agentmain.py:38`），由 `llmcore.py:1225-1226` 每轮 `set_system()` 真正下发。
3. 模型看到 `L3: ... | ljqCtrl_sop+.py | tmwebdriver_sop | ...`（`memory/l1_fallback.txt:5-6`）→ 决定 `file_read('../memory/tmwebdriver_sop.md')`。
4. `zicat.py:444-445` 在工具结果后追加提示：`[SYSTEM TIPS] 正在读取记忆或SOP文件，若决定按sop执行请提取sop中的关键点（特别是靠后的）update working memory.` —— **"特别是靠后的"** 是在对抗"只读开头就动手"（坑写在末尾）。
5. `update_working_checkpoint` → `zicat.py:452-461` 写入 `self.working['key_info']` → 之后每轮由 `_get_anchor_prompt()`（`zicat.py:537-547`）注入 `<key_info>`。
6. `zicat.py:158-166` 顺手记一次访问计数（无人消费）。

**结论：召回 = "索引文本 + 模型自觉读文件"，不是向量检索、不是工具自动挂载。** 这解释了为什么 L1 只有 23 行——它就是给模型看的目录页。

## 2. 进化有没有质量控制？——五道文本关，代码关只有两道

## 文本层：五道关（全部由 SOP 自规定）

| 关 | 位置 | 内容 |
|---|---|---|
| ① 公理关 | `memory_management_sop.md:1-14` | 四条公理：**Action-Verified Only（"No Execution, No Memory"）**、**神圣不可删改**、**禁止易变状态**、**最小充分指针** |
| ② 分层关 | `memory_management_sop.md:76-95` | 决策树：环境事实→L2；通用规律→L1 RULES；特定任务技术→L3；其他→丢弃 |
| ③ 容量关 | `memory_management_sop.md:28-40` | L1 硬约束 ≤30 行 / <1k tokens；禁写密码；禁 How-to |
| ④ 压缩关 | `memory_cleanup_sop.md:23-29`「压缩四原则」 | 命名自解释 > 加描述；存在性集合最小描述；条目=场景↔方案；分层归位 |
| ⑤ 审计关 | `memory_cleanup_sop.md:52-59`「L3 内容审计」 | 删：无触发条件的"必须全覆盖"、已被推翻的旧结论、过时人际规则、重复免责声明、**"从未证明有用的防御仪式（说不出它哪次真抓到过问题，就删）"** |

最有信息量的是 `memory_cleanup_sop.md:12` 的 ROI 公式：
`ROI = (不放这几个词的犯错概率 × 代价) / 每轮词数成本` —— 把"记忆该不该留"变成可算的量。
`memory_cleanup_sop.md:37` 还有一条可机械核对的"幽灵条目审计"：**L1 指向的 L3 文件是否真实存在？**

## 代码层：只有两道，而且都很软

| 代码关 | 位置 | 实际强度 |
|---|---|---|
| L1 体积检查 | `zicat.py:519` `if (l1 := load_L1()) and len(l1) > 6000: result += 'L1 (insight or index) is too large, follow L0 and cleanup sop to fix it!'` | **软**：只在 `start_long_term_update` 被调用时检查；阈值 6000 字符（远超"30 行"）；不阻断 |
| 读后提醒 | `zicat.py:444-445` | 纯提示，不拦截 |
| "只 patch 不 overwrite"纪律 | `memory_management_sop.md:9,39`；`memory_cleanup_sop.md:41` | **纯文本**：代码没有任何"禁止 overwrite memory/" 的守卫 |

**这是本仓库最实在的一处"文档强于代码"**：`≤30 行` 是文档里的"硬约束"，代码里对应的只有一次性 `>6000 字符` 的软提醒；若模型不调用 `start_long_term_update`，这套检查一次都不会跑。

## 自动化程度

- **L4 归档 cron 是真自动的**：`reflect/scheduler.py:63-74`，`if _time.time() - _l4_t > 43200`（12h）→ `from compress_session import batch_process` → 压缩 `temp/model_responses/` 到 L4；`memory/memstore/l4_compress.py:43-68` 是压缩实现，`:59` 有"压缩后 <4500B 丢弃"的防噪声门槛。
- **scheduler 单例靠端口锁**：`reflect/scheduler.py:7-9` 用 `socket.bind(('127.0.0.1', 45762))` 占端口，"bind 失败即崩"来防重复启动。
- **没有"记忆 GC 的自动化"**：`memory_cleanup_sop.md` 在全仓 `.py` 里**零引用**（grep 只命中 `frontends/review_cmd.py` 的 `review_sop`）。防膨胀是**流程规范**，不是**定时任务**。

## 主循环（`agentmain.py:298-342`，共 45 行，是全仓最划算的一段代码）


**模块契约**（全部是可选的模块级属性/函数，没有基类、没有注册表）：

| 契约 | 类型 | 作用 |
|---|---|---|
| `check()` | 必填 | 返回 `None`（不唤醒）/ 字符串（唤醒并把它当 user prompt）/ `'/exit'`（退出循环） |
| `INTERVAL` | 可选 | 轮询间隔秒，默认 5 |
| `ONCE` | 可选 | True 则跑完一次就退出 |
| `init(argv_dict)` | 可选 | 接收未知命令行参数（`--base_url xx` → `{'base_url': 'xx'}`，`agentmain.py:246`） |
| `on_done(result)` | 可选 | 拿到本轮 `done` 全文做状态回写 |
| `LLM` | 可选 | 模型名，命中则 `next_llm()` 切过去 |

**"无人值守"的三个支点**：① `check()` 里先做廉价预检，没事就 `return None`（不花 token）；② 有事件才 `put_task`，然后**同步等 done**（`dq.get(timeout=2200)`，2200 秒兜底）；③ caller 是 `while True` + `time.sleep`，进程只要不被杀就一直转。

## 一个容易误解的点：UI 的"空闲 30 分钟自动干活"不走 reflect

`frontends/qtapp.py:2453-2472` 自己起了一个 `QTimer(5000)`，在 `idle > AUTO_IDLE_THRESHOLD(1800)` 时调 `panel.inject_message("[AUTO]🤖 用户已经离开超过30分钟...")`；`frontends/stapp.py:85` 里有同一句英文 prompt 常量。**它把 prompt 硬编码在 UI 里，没有 import `reflect/autonomous.py`**。所以：

- "UI 空闲触发" = 前端定时器 + 往当前会话塞一条 prompt（在同一个 agent 会话里继续）。
- "reflect 无人值守" = 独立进程 + `check()` 轮询 + `put_task`（可以是另一个模型、另一份上下文）。

两者文案相同，机制完全不同。**把 `reflect/autonomous.py` 理解为"autonomous 模式的入口"是错的**——它只是最简 demo。

## 边界（`--reflect` 做不到的事）

- **没有守护/重启**：进程挂了就没人管。`--task`/`--func` 模式有"后台 spawn 自己"（`agentmain.py:248-259`），`--reflect` 没有。
- **没有并发**：`check()` 同步等 `done`，一次只能跑一个任务；想并行只能起多个进程（goal_team 就是这么干的）。
- **`check()` 异常被吞**：`agentmain.py:321-322` 捕获后 `task=None` 继续转，错误只在 stdout 打一行。
- **热重载会重跑 `init()`**（`:317`），但模块级全局量不会重置（`exec_module` 复用同一个 `mod` 对象的 `__dict__`，`scheduler.py:5-9` 的 `try: _lock except NameError` 就是专门为这个写的）。

**结论（重要）**：
1. **"多智能体"在本仓库 = 多个独立进程，每个进程里是同一个单 agent 循环**。没有共享内存状态机、没有消息幂等、没有分布式锁，协作协议**全部写成 SOP 文本**（`goal_team_sop.md`、`checklist_sop.md`、`subagent.md`），共享状态只有一个"BBS + sqlite"和"共享文件系统"。
2. 唯一有"调度语义"的代码是 `reflect/scheduler.py`（定时）和 `conductor.py`（事件驱动）；`goal_mode.py` 只是"按预算反复唤醒同一个 agent"。
3. 所以更准确的表述是：**单 agent 循环 × 多进程复制 + 文本协作协议 + BBS/文件作共享介质**。README 的 "多 Agent 委派" 在 `conductor.py` 里是真的（同进程多实例），但复杂度远低于"多智能体框架"这个词给人的预期。

## 一个反直觉的结论

**"自我进化"里真正被代码保证的只有"索引每轮必现"这一件事**（`zicat.py:581-591` → `agentmain.py:38`）。剩下全是"让模型在这样的上下文里自己动":
- 索引每轮必现 → 模型永远知道自己"曾有过什么能力"；
- `start_long_term_update` 在长任务末尾被工具描述点名 → 抬高沉淀概率；
- `DANGER turn%17` 明写 "Re-read relevant SOPs" → 制造"回看记忆"的周期冲动；
- `turn%15` 重放 L1 → 对抗长上下文里索引沉底。

这四条合起来，形成一个**高概率回路**：跑得越久 → 越可能被提醒"该沉淀/该回看" → 越可能把经验写进 L3 → 下次 L1 索引里有它。它不是"自动学习"，而是**把学习行为的发生概率调到很高**。这就是 README 说"用几周后拥有专属技能树"（`README.md:686`）能成立的真实原因，也是它脆弱的地方：概率 = 模型的服从度。

## 8. 复刻 checklist（迁到自己的 Agent 时）

### P0 必须保留（删掉就不是同一个东西了）

- [ ] **单一"自然结束"出口**：模型不调工具 ⇒ 引擎注入 `no_tool` ⇒ 只有 `no_tool` 能返回"结束"。**绝不让模型用文字宣布完成**。（`agent_loop.py:69,91-92`）
- [ ] **坏响应检测 + 三振出局**：空响应、流中断标记、`</summary>` 半截、max_tokens 截断、非法工具格式，五类都塞回 `[ERROR] ... Regenerate and tooluse`；连续 3 次才 `should_exit`。
- [ ] **`<summary>` 强制并入库**：每轮抽取 80 字快照 append 到 `history_info`，供后续锚点提示复用。这是"长任务不丢信息"的最低成本方案。
- [ ] **周期提醒三连**（DANGER）：`T%17`=存工作记忆+重读 SOP；`T%41`=写文件别只写 checkpoint；`T%175`=找用户收口。阈值可调，但**三个不同粒度必须并存**。
- [ ] **工作记忆锚点 + 历史折叠**：每轮注入 `key_info`，历史按 `%2` 注入近 30 条、`%4` 注入折叠后的早期上下文（折叠成 `[Agent]（N turns）`）。
- [ ] **工具级超时强杀**：`timeout` 上限（zicatAgent 是 600s）+ 轮询 `kill`，并把"超时/被终止"写进工具输出（模型需要看到失败原因）。
- [ ] **用户中断能真的断掉网络读**：`should_stop` + 关掉 in-flight socket。**只设标志位不关 socket 是假的 abort**。
- [ ] **沉淀闭环的最小件**：一个"该沉淀了"的显式工具/指令 + 一份 L0 元 SOP + 一份 ≤30 行的 L1 索引，三件缺一不可。

### P1 值得迁移

- [ ] **索引每轮全量注入**（L1 只有 20-30 行，成本可忽略，但决定"能力可被发现"）。
- [ ] **`start_long_term_update` 式的"叫醒而不是代写"**：让模型自己在 L0 约束下改写记忆，但**你必须给它一个"读 L0 再动手"的强制顺序**（zicatAgent 的做法：工具结果里直接回填 L0 全文）。
- [ ] **"大代码块未执行"检测**：模型极爱用代码块冒充执行，这条拦截性价比很高。
- [ ] **`_done_hooks` 自调度**：允许流程在"本该结束"时插一条自检 prompt（zicatAgent 的用法见 `memory/autonomous_operation_sop.md:26`）。⚠️ 注意这是**未公开能力**，需要 `inline_eval` 才能塞进去；如果你的框架不允许执行内部对象，换成"结束前必答自检题"更安全。
- [ ] **`--reflect` 那种 45 行轮询循环**：`check() -> None|str|'/exit'` 三态契约 + `INTERVAL` + `ONCE` + `on_done` + 热重载（`mtime` 变化即重载）。极简到几乎没有框架，可移植性最好。
- [ ] **多 session failover + 指数退避**（`llmcore.py:1162-1193`）。这是"外部世界不配合"时的真实执行力。
- [ ] **调度器做"窗口+冷却"而不是"到点就跑"**：`max_delay_hours`（开机太晚就跳过）+ 冷却比周期略短（`daily→20h`）防漂移。见 `reflect/scheduler.py:29-49,105-117`。

### 可以换掉（zicatAgent 的实现方式只是其中一种）

- [ ] **纯文本 SOP 索引 + 模型自读文件** ⇒ 可换成工具注册表/技能加载器（如 MCP tools、skill 目录自动挂载）。zicatAgent 这么做的唯一原因是"零代码扩展"，代价是召回全靠模型自觉。
- [ ] **BBS + sqlite + 文件系统 当协作介质** ⇒ 换成正经的消息队列/任务表，能拿到幂等、重试、超时、可见性。
- [ ] **`_fold_earlier()` 用"行数"折叠历史**（`zicat.py:523-535` 只保留最后 70 段）⇒ 换成按 token 预算 + 结构化摘要。
- [ ] **`file_access_stats.json` 这种无人消费的埋点** ⇒ 要么接上"低访问记忆自动降级"的清理逻辑，要么删掉。
- [ ] **`plan_*` 双轨残留**（后端已弃用、前端仍在解析）⇒ 迁移时别复制这种"两套状态机"。
- [ ] **17/41/175 这种魔法数字** ⇒ 保留"三个粒度"的设计，但把阈值做成配置并注明依据（仓库里没有任何调参说明，属〔未验证〕）。

### 迁移时最容易踩的三个坑

1. **把"提示词里的纪律"当"机制"**。`sys_prompt.txt:6` 的"3 次失败换方案"没有任何代码强制，别指望它。要真强制，就得像 `_empty_ct` 那样有计数器。
2. **只做 abort 标志位不做 socket 关闭**。zicatAgent 的注释（`agentmain.py:133-140`）明确指出 `shutdown()/close()` 唤不醒阻塞的 recv，必须绕过引用计数真的 `closesocket`。这一点在 Windows 上尤其隐蔽。
3. **让模型自己维护索引却不给"容量硬检查"**。zicatAgent 这里恰恰是弱点（`zicat.py:519` 只警告 6000 字符）。迁移时建议直接做成"写入前校验 L1 行数，超限拒绝写入并返回清理指令"。
