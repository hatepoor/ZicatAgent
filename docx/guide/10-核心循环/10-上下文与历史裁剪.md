`agent_loop.py` 只有 132 行，`zicat.py` 590 行，但 `llmcore.py` 有 1270 行。**框架真正的复杂度在这里**：模型适配、流式解析、历史裁剪、故障切换。

## 三个"历史"概念，别搞混

| 概念 | 存在哪 | 格式 | 谁写 | 用途 |
|---|---|---|---|---|
| `backend.history` | 内存（Session 对象） | Claude content-block 列表 | 每次 `ask()` 追加 | **发给模型的唯一真相** |
| `handler.history_info` | 内存（列表） | `[USER]: ...` / `[Agent] 摘要` 文本行 | `turn_end_callback`、`run()` | 拼 `<history>` 块给模型看 |
| `temp/model_responses/*.txt` | 磁盘 | `=== Prompt ===` / `=== Response ===` | `_write_llm_log`（`llmcore.py:1079-1087`） | 事后审计、L4 归档原料、`/resume` 恢复 |

代码里**没有** "MR" 这个概念（全仓 grep 无命中）。所谓"会话恢复"是从日志文件里正则抠 `<history>` 块（`memory/memstore/l4_compress.py:87`）。

## 双轨客户端：原生函数调用 vs 文本协议

这是"高兼容性"的实现方式，两条完全不同的路径：

```
                      ┌─ NativeToolClient（原生）─────┐
resolve_client() ─────┤  Claude/GPT 原生 function call │
   llmcore.py:1263    │  system 每轮随 payload 发      │
                      │  tool_calls 由 API 返回        │
                      └───────────────────────────────┘
                      ┌─ ToolClient（文本协议）────────┐
                      │  把整个对话拍平成一段文本       │
                      │  工具 schema 当文本塞进 prompt │
                      │  从回复里正则抠 <tool_use>     │
                      └───────────────────────────────┘
```

**`ToolClient` 的拍平方式**（`llmcore.py:993-1008`）：

```python
system = system_content + tool_instruction      # 角色 + 交互协议 + 工具 JSON
user   = ""
for m in history_msgs:
    user += f"=== {role} ===\n"
    user += "".join(f'<tool_result>{tr["content"]}</tool_result>' for tr in m['tool_results'])
    user += str(m['content']) + "\n"
user += "=== ASSISTANT ===\n"
return system + user
```

然后把 `system+user` 整段当成**一条 user 消息**追加进 `backend.history`，由 `_msgs_claude2oai` 转成 OpenAI 格式。模型看到的是一份"伪对话记录"。

**省 token 的两个小机关**：

1. `auto_save_tokens`（`llmcore.py:987-990`）：如果这一轮的工具 schema 和上一轮**完全一样**，就不重发 5.6KB 的 JSON，只发一句"工具库状态：持续有效"。
2. `total_cd_tokens > 9000` 时清空 `last_tools` 逼重发（`llmcore.py:1006`），`agent_loop.py:56` 每 10 轮也清一次——防止"模型忘了有哪些工具"。

**原生路径则干净得多**：`NativeToolClient.chat`（`llmcore.py:1219-1253`）把本轮 delta 组装成一个 user 消息（`tool_result` block + 文本），`set_system()` 每轮把系统提示写进 `backend.system`，由 `raw_ask` 随 payload 发送（`llmcore.py:859-863`）。

> **复刻提醒**：两条路径的语义不完全等价。文本协议下系统提示只存在于历史第一条消息里，会被后续裁剪稀释；只有每 15 轮的 `<global_memory>` 重注入在补。原生路径没有这个问题。如果只做一条，优先做原生。

## 上下文裁剪：两道闸门的完整逻辑

每次 `ask()` 追加消息后立刻调用 `trim_messages_history(history, self)`（`llmcore.py:724`、`:876`）。

**闸门 A：`compress_history_tags` —— 位置不动，内容打折**（`llmcore.py:77-109`）

- 每 `cut_msg_interval` 次调用才真正跑一次（计数器是**函数属性**，全局共享，`llmcore.py:79-81`）；
- 只处理"除最近 10 条以外"的老消息（`llmcore.py:90-91`）；
- 老消息里的 `<thinking>` / `<tool_use>` / `<tool_result>` 超过 800 字符就砍成"头 400 + `...[Truncated]...` + 尾 400"；
- **最关键的一条**：`<history>` / `<key_info>` / `<earlier_context>` / `<global_memory>` 四种块**整块折叠成 `[...]`**（`llmcore.py:84`、`:87`）。

这一条解释了整个设计：**工作记忆是每轮重注入的，所以历史里的旧副本可以毫无心理负担地抹掉**。上下文成本于是变成一个常数（每轮注入多少），而不是随轮数增长的累加量。

**闸门 B：`trim_messages_history` —— 直接砍消息**（`llmcore.py:136-160`）

```python
cap    = sess.context_win * 3                      # :137  默认 38000*3 = 114,000 字符
target = int(cap * sess.trim_keep_rate)            # :138  默认 0.6 → 68,400 字符
compress_history_tags(history, interval=...)       # :141  先做轻压缩
if c <= cap: return                                # :143  没超限就到此为止
compress_history_tags(history, keep_recent=4, force=True)   # :144  超限则激进压缩
while len(post) - i > 9 and c > target:            # :147  从头丢消息，对齐到 user 轮
    ...
    post[i] = _sanitize_leading_user_msg(post[i])  # :150  首条 user 的孤立 tool_result 降级为文本
history[:] = pre + gap + post                      # :158  必要时插 "..." 修补 user/assistant 交替
```

几个精妙处：

- **预算是字符不是 token**。`cost()` 用 `len(json.dumps(m))` 求和（`llmcore.py:140`）。粗糙，但零依赖、零分词器，且对中文/英文混排不会差太远。
- **砍完还要修协议**。Anthropic 要求 `tool_use`/`tool_result` 配对、user/assistant 交替。砍掉一半会留下孤立块 → `_sanitize_leading_user_msg`（`llmcore.py:111-126`）把孤立 `tool_result` 改写成纯文本，`gap` 消息修补角色交替。
- **保底 9 条**（`len(post) - i > 9`），避免砍到没有上下文可用。

**数字推导（"<30K 上下文"的真实来源）**

| 配置 | `context_win` | `trim_keep_rate` | cap（字符） | target（字符） | 折算 tokens（按 3 字符/token） |
|---|---|---|---|---|---|
| 默认 | 38,000 | 0.6 | 114,000 | 68,400 | ≈ 22.8K |
| 模型名含 deepseek | 80,000 | 0.3 | 240,000 | 72,000 | ≈ 24.0K |

两种默认配置的稳态都落在 **~23K tokens**。这就是 README 说"<30K 上下文"的来源。注意：**代码从不统计 token**，这是配置反推值。

## MixinSession：多模型故障切换

`MixinSession`（`llmcore.py:1100-1193`）把多个 session 包成一个门面：

- `raw_ask` 里按 `(base + attempt) % n` 轮转，检测错误前缀（`!!!Error:` / `[Error:`）；
- 成功就记住当前节点，`spring_back` 秒后回落到主节点（`llmcore.py:1155`）；
- 流中断（`[!!! 流异常中断`）也会主动切下一个节点（`llmcore.py:1180-1182`）；
- 用 `copy.copy` 复制 session、共享同一份 `history`，保证切换不丢上下文（`llmcore.py:1121`、`:1129`）。

这是生产可用性的关键：单一 API Key 挂掉时任务不中断。代价是 `_FACADE_STATE`/`_TRANSPORT_OVERRIDES` 那套属性转发很绕（`llmcore.py:1102-1149`），自己造时建议简化成显式代理。

## 为什么这套能撑住 180 轮

把三件事叠起来看：

1. **历史被裁剪**（闸门 A/B）→ 上下文不爆；
2. **工作记忆被重注入**（`_get_anchor_prompt`）→ 裁剪造成的"失忆"被补上；
3. **全局索引每 15 轮重放**（`zicat.py:565`）→ 长任务中不会忘记自己的能力和宪法。

换句话说：**ZicatAgent 不是把上下文做大，而是把"必须记住的东西"做得极小、极稳，然后允许历史被无情丢弃。** 这是它能在 30K 级上下文里跑 180 轮的根本原因，也是它比"200K 上下文 + 全量历史"方案更省 token 的原因。
