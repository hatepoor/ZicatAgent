## 工具 = 一个 `do_` 方法 + 一条 schema

没有注册表。`BaseHandler.dispatch`（`agent_loop.py:18-29`）用反射：

```python
method_name = f"do_{tool_name}"
if hasattr(self, method_name):
    args['_index'] = index; args['_tool_num'] = tool_num
    ret = yield from try_call_generator(getattr(self, method_name), args, response)
    return ret
elif tool_name == 'bad_json': ...
else:
    yield f"未知工具: {tool_name}\n"
    return StepOutcome(None, next_prompt=f"未知工具 {tool_name}")
```

**加工具的成本 = 改两个文件**（handler 加方法，`assets/tools_schema.json` 加描述）。这是它比 LangChain 式插件系统轻的地方，也是它没有任何权限/沙箱/审计的地方。

三个必须知道的细节：

1. **schema 不是注册表，只是给模型看的说明书**。没有任何 `register_tool` / `TOOLS_SCHEMA.append` 的 API（全仓 grep 无命中）。所以"动态创建新工具"（README 的说法）在代码里不存在，实际路径是 `code_run` 写脚本 + 存 SOP。
2. **没有工具白名单**。`hasattr(self, "do_" + name)` 意味着模型只要猜出方法名就能调用任何 `do_*`，包括 schema 里故意不公开的 `do_no_tool`（`zicat.py:468`）——模型可以主动调 `no_tool` 直接结束任务。
3. **schema 在运行时会被改写**。`ToolClient.chat`（`llmcore.py:945-954`）把 `file_write` 的 `content` 参数**删掉**，逼模型把内容放进 `<file_content>` 标签；非 Windows 上 `agentmain.py:21` 直接字符串替换 `powershell → bash`。同一份 schema，两条协议下发给模型的定义并不相同。

## 9 个原子工具的真实职责

| 工具 | 实现 | 真实作用 | 关键设计 |
|---|---|---|---|
| `code_run` | `zicat.py:303-329` | 万能兜底：Python 脚本 / PowerShell 单行 | 写临时 `.ai.py` 文件再执行，注入 `code_run_header.py` 修编码 + 设提示钩子；超时/停止信号可杀进程 |
| `file_read` | `zicat.py:428-446` | 读文件，支持 keyword 搜索 | 找不到文件时用 `difflib` 给相似文件名建议（`zicat.py:256-266`） |
| `file_write` | `zicat.py:394-426` | 整文件写 | 内容必须放 `<file_content>` 标签；>5000 字符追加"写太长，小心幻觉"警告 |
| `file_patch` | `zicat.py:380-392` | 唯一匹配替换 | 0 匹配/多匹配都报错并给改进建议；支持 `{{file:path:start:end}}` 引用展开 |
| `web_scan` | `zicat.py:338-351` | 看网页（简化 HTML） | 经 `simphtml` 做"密度驱动"简化 |
| `web_execute_js` | `zicat.py:353-378` | 在真实浏览器里执行 JS | 结果可存文件；有页面变化监控；`no_monitor` 省 2-3 秒 |
| `ask_user` | `zicat.py:331-336` | 打断任务问人 | 返回 `should_exit=True`，是唯一"合法中断" |
| `update_working_checkpoint` | `zicat.py:452-461` | 工作便签 | 覆盖式，<200 token，每轮自动注入 |
| `start_long_term_update` | `zicat.py:509-521` | 触发记忆沉淀 | 只注入规范，不写文件 |
| （隐藏）`no_tool` | `zicat.py:468-507` | 引擎内部伪工具 | 5 类坏响应检测 |

## 为什么 9 个就够

因为 `code_run` 是**图灵完备的兜底**：

- 缺依赖 → `pip install`（`code_run` 跑 shell）；
- 缺能力 → 写个脚本，脚本就是新能力；
- 缺工具 → 脚本写好后存进 `memory/*.py`，下次 `code_run` 直接调。

所以"扩展工具"这件事不需要改 schema，只需要**一次成功的 `code_run` + 一条 SOP 记录**。这是"9 个工具"能成立的根本原因，也是它和"工具越多越好"路线最根本的分歧。

## 长度控制：三道闸 + 一个乘法器

工具输出是上下文爆炸的主要来源，这套系统用三层拦截：

**第一道：每个工具的字符预算**（`zicat.py:291-293`）

```python
def _get_tool_maxlen(self, l, args, growth_rate=1.0):
    multiplier = 1 + (self.parent.get_ctx_multiplier() - 1) * growth_rate
    return int(l * multiplier / args.get('_tool_num', 1))
```

`multiplier` 来自 `min(max(context_win / 默认窗口 × 0.75, 1), 3)`（`llmcore.py:673-678`）——**按 `mykey.py` 里配置的 `context_win` 缩放，模型名只影响分母**（含 deepseek 时分母 80000，否则 38000）。

| 工具 | 基数 | 缩放曲线 | multiplier=3 时 |
|---|---|---|---|
| `code_run` | 10,000 | 正常 | 30,000 |
| `file_read` | 15,000 | 正常 | 45,000 |
| `web_scan` | 35,000 | **半速**（`growth_rate=0.5`） | 70,000 |
| `web_execute_js` | 8,000 | 正常 | 24,000 |

同轮多个工具时再除以 `_tool_num`——保证"单轮工具输出总量 ≈ 单工具上限"。

**第二道：`smart_format` 掐头留尾**（`zicat.py:269-272`）——超过预算就保留前一半 + ` ... ` + 后一半。注意**掐掉的是中间**，日志里的关键错误可能正好在中间。

**第三道：跨轮历史压缩**（第 2.3 节的闸门 A/B）。

还有一个被忽视的成本：`next_prompt` 通道**没有长度上限**——每轮的工作记忆、每 15 轮重放的 L1、`start_long_term_update` 注入的 L1 全文，都走这条路。这是固定开销，绕过了上面三道闸。

## 浏览器真实性：`TMWebDriver` + `simphtml`

不是 Playwright/Selenium，而是：

```
Agent ──WS:18765 / HTTP:18766──► 本地 server (TMWebDriver.py)
                                      ↕  (ack / results 按 tab 分发)
                              Chrome 扩展（内容脚本注入页面）
                                      ↕
                              用户自己的真实 Chrome（cookie / 登录态 / 指纹）
```

扩展在页面的 **MAIN world** 里 `eval` 脚本；CSP 拦截时降级到 `chrome.debugger` 的 `Runtime.evaluate`。它没有自动化 flag，`disable_dialogs.js:2` 直接把 `navigator.webdriver` 删掉——所以 README 里那些反检测通过率是有机制解释的（具体分数本次未复现）。

对比无头浏览器：

- 无头浏览器 = 新起一个"假人"，没有登录态，指纹可被检测；
- TMWebDriver = **操作你自己的浏览器**，登录态、扩展、GPU、WebGL 全是真的；
- 代价 = 依赖用户的 Chrome 一直开着 + 扩展被注入，且**没有降级路径**（Chrome 没开就全废）。

`web_scan` 靠 `simphtml` 做简化，核心思想是**用几何而不是语义判断重要性**——决策全部发生在浏览器里（两段共 594 行的注入 JS）：

1. `findMainList`：不看文本，只看结构频次和面积，找出"列表容器"；
2. `js_optHTML`：克隆可见 DOM，用 `getBoundingClientRect` + `getComputedStyle` 算面积/可见性/z-index，用 `document.elementFromPoint(视口中心)` 反查谁在最上层（ground truth，不猜 z-index），把节点标成 `main / secondary / nonEssential`，浮层广告整棵删除；下拉菜单特判保留；
3. Python 侧瘦身：`svg` 清空、`style` 删、长 url 换成 `__url__`、属性白名单；
4. `cutlist`：长列表只留前 3 条，插一句 `[FAKE ELEMENT] N more items hidden, selector: "..."`；
5. `smart_truncate`：按字符预算**递归分摊**截断。

**有损边界**：第 4 步之后，模型看不到第 4 项以后的内容，必须知道要用 `web_execute_js` 按 selector 精确取。这个坑 README 没写，但 SOP 里写了。

另一个省 token 的关键设计：`execute_js_rich` 会在执行后做**结构化 DOM diff**（`simphtml.py:672-703`），返回"DOM 变化量 + 最显著变化"。模型不必每步 `web_scan` 就能确认动作是否生效。

## 工具层的六个风险

1. **任意代码执行（最高危）**：`code_run` 用当前用户权限跑任意 Python/PowerShell，无沙箱、无目录限制、无网络限制。`inline_eval=True` 更狠——**直接在 Agent 进程内 `eval`**，命名空间暴露 `handler`/`parent`/`history`（`zicat.py:317-326`），模型可以改 `parent.llmclient`、读出 `mykey.py` 里的 API Key、甚至 monkeypatch 工具方法。schema 只写了 "DO NOT USE"，没有任何技术拦截。
2. **路径逃逸**：`_get_abs_path` 只做 `abspath(join(cwd, path))`（`zicat.py:294-296`），绝对路径和 `../../` 直接生效——`file_*` 三个工具可读写进程能碰到的任何文件（含 `mykey.py`、`.git/`）。`expand_file_refs` 还是个现成的跨文件内容搬运通道。
3. **超时/僵死/半死**：`code_run` 只 `kill()` 直接子进程，孙进程成孤儿；杀掉后 `poll()` 可能返回 `None`，模型会看到"失败 + 进行中"的矛盾状态。更糟的是 `web_execute_js` 超时后**返回 `status:"success"`** + 一句"No response data in 15s"，而脚本可能还在页面里跑。
4. **浏览器单点依赖**：`driver` 是模块级全局单例，首次调用最多等 14 秒，第 5 次失败还会主动 `webbrowser.open('https://example.com')`。Chrome 没开就 `web_*` 全废，没有降级到 HTTP 抓取或 headless 的路径。
5. **协议层的裸奔**：`agent_loop.py:70` 对原生 tool_call 的 `json.loads(arguments)` **没有 try**——一个坏 JSON 就让整个任务以 `Backend Error` 结束。文本协议有 `bad_json` 兜底，原生协议没有。这是两条路径不对等的一个典型例子。
6. **语义风险**：简化 HTML 是有损的（cutlist 只留 3 项），模型若假设"没看到就是没有"会误判页面；`next_prompts` 是 `set`，多工具时顺序不确定；`key_info` 无长度校验，可被无限撑大。
